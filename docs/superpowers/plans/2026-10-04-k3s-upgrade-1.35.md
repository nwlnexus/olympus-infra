# k3s Upgrade to v1.35 — Implementation Plan

> **Design:** [`../specs/2026-10-04-k3s-upgrade-1.35-design.md`](../specs/2026-10-04-k3s-upgrade-1.35-design.md)
> **Repos:** `olympus-gitops` (SUC, plans, add-ons), `olympus-infra` (k3s role, kube-vip, pins, health gate).
> **Rule:** every change is a PR. By hand only: snapshots, health checks, the naraka-01 hold label, deleting the bare kube-vip Pod and the Longhorn webhooks, and uncordon after a fix-forward.

## Model per task

| Work | Model | Why |
|---|---|---|
| Review of this spec/plan; go/no-go at the Phase 0 exit, before Hop 1 and before Hop 2 | **fable** | Highest stakes: etcd quorum, point of no return, restore-only rollback |
| Health-gate script, kube-vip DaemonSet, SUC install, running each hop | **opus** | Infrastructure work with judgement at every gate |
| cert-manager / Flux / ESO version steps, Longhorn removal | **opus** | CRD storage versions, webhooks, ordering |
| Converting 22 ESO manifests to `external-secrets.io/v1` | **sonnet** | Mechanical, clear spec |
| Triage of gate output and logs between hops | **haiku** | Cheap and repetitive |

## Hop procedure (Hops 1–4)

Avoid 00:00 and 12:00 UTC, when the scheduled etcd snapshots run.

1. Health gate → PASS.
2. Prepare the restore path; **do not merge the Plan until both exist**:
   - `scripts/k3s-snapshot.sh pre-<version>`; it must report the copy on styx with a matching size and sha256.
   - On **each** server: `cp -p /usr/local/bin/k3s /usr/local/bin/k3s-<current version>`. Verify the copy's sha256 equals `/usr/local/bin/k3s` on all three.
3. **Hold two servers.** SUC uncordons a finished node and starts the next one immediately, so per-server checkpoints need holds. Label all but the first server: `kubectl label node <server> plan.upgrade.cattle.io/server-plan=disabled`.
   - Order: **onode-0312ce** first (not the etcd leader or the VIP holder), then onode-0314ac, then **onode-030c31** last, so the leader election and VIP move happen in isolation.
4. PR, then merge:
   - set the SUC ConfigMap kubectl image for this hop (design §3);
   - create or update `server-plan` (design §4) with `version: <version>`.
5. Watch `kubectl -n system-upgrade get plans,jobs,nodes -w`. When the active server's job completes:
   - Expected and not a failure: after the Plan PR merges, Flux Kustomizations show `DependencyNotReady` for about 2–3 minutes while the new revision works down the dependency chain. Wait until all of them have applied the new revision before the first gate. Each upgrade job also leaves one Failed pod (k3s kills it while restarting); the gate allow-lists it and checks job success separately (`suc.jobs`).
   - Run the health gate with the transition values in `scripts/k3s-health-gate.conf`, e.g. `EXPECTED_ETCDSERVER="<old> <new>"` and `EXPECTED_SERVER_K3S_VERSION="<old> <new>"`. Member IDs must be unchanged.
   - Hop 1, first server only: compare pod start times on that node before and after (design §2.5). Containers that restarted during the containerd restart are the signal to assess, not to wave through.
   - Gate passes → release the next server: `kubectl label node <next> plan.upgrade.cattle.io/server-plan-`.
   - Any failure, or a node not `Ready` in 10 minutes → **stop rule** (design §6). Held servers stay held.
6. All three servers on the version → set the conf to the single new values (`EXPECTED_ETCDSERVER`, `EXPECTED_SERVER_K3S_VERSION`) and run the full gate. Then soak (design §8) and the hop's post-steps.
