# k3s Control-Plane Upgrade to v1.35 — Design

> **Status:** Reviewed draft (2026-10-04). An independent review's blockers and should-fixes are folded in.
> **Plan:** [`../plans/2026-10-04-k3s-upgrade-1.35.md`](../plans/2026-10-04-k3s-upgrade-1.35.md).
> **Owner decisions:** §5 Longhorn (remove, recommended), §8 soak times.

## 1. Problem

| Node | Role | k3s | containerd | OS |
|---|---|---|---|---|
| onode-030c31 | server, etcd (cluster-init); currently etcd leader and kube-vip holder | v1.32.4+k3s1 | 2.0.4 | Ubuntu 24.04, kernel 6.8, cgroup v2 |
| onode-0312ce | server, etcd | v1.32.4+k3s1 | 2.0.4 | same |
| onode-0314ac | server, etcd | v1.32.4+k3s1 | 2.0.4 | same |
| naraka-01 | agent (`olympus.io/role=management-hub:NoSchedule`) | **v1.35.5+k3s1** | 2.2.3 | Ubuntu 25.04, kernel 6.14 |

**Current state:**
- **1.32 is end of life.**
- **naraka-01 is out of support.** Its kubelet is three minors newer than the API server, which the Kubernetes skew policy forbids ("kubelet must not be newer than kube-apiserver"). It was installed with no version pin, so it got `latest`.

**Goal:** all four nodes on **v1.35.9+k3s1**, with the pin applied at install time from now on.

**Non-goals:**
- **v1.36:** later, as its own change.
- **naraka-01's OS:** Ubuntu 25.04 is end of life and needs its own change.

## 2. Constraints

1. **One minor at a time,** servers before agents, one server at a time.
2. **etcd 3.5 → 3.6 passes through 3.5.26.** v1.32.4 ships etcd 3.5.21 and v1.33.13+k3s2 ships 3.6.14, so the first hop is **v1.32.13+k3s1** (etcd 3.5.26-k3s1).
   - **Why:** k3s release notes and the etcd "zombie members" post: skipping it can resurrect removed members.
   - **Risk is low here:** the same 3 members have been in place for 177 days.
   - **The waypoint is cheap, so keep it.** Upstream etcd now says 3.5.32; no k3s 1.32 ships that, and k3s documents 3.5.26.
3. **Exact versions, never channels.** `stable` resolves to v1.36.5 today.
4. **No downgrades.**
   - k3s-upgrade refuses them.
   - The control plane goes back only by snapshot restore.
   - **Point of no return:** once etcd reports `etcdcluster: 3.6.0` after Hop 2, the only way back to 1.32 is the `pre-v1.33.13` snapshot, losing every write since.
5. **Storage is single-attach.** All 12 PVCs are `qnap-iscsi` RWO, 11 attached, used by single-replica workloads.
   - **Servers are cordoned, never drained.** No Plan ever sets `drain`; the redpanda PDB would block it.
   - **k3s runs with `KillMode=process`,** so container shims survive a k3s restart.
   - **Each hop also replaces containerd** (2.0.4 → 2.1.5 → 2.2.5 → 2.2.7), which restarts and re-attaches to the shims. Expect pods to stay up, but confirm pod uptimes on the first server of Hop 1 before relying on it.

## 4. Mechanism: system-upgrade-controller via Flux

**Choice:** system-upgrade-controller (SUC) **v0.20.2** (latest, released 2026-09-23), deployed by Flux from `olympus-gitops` at `clusters/olympus/system-upgrade/`. A hop is a one-line `version:` change in a PR.

**Rejected alternative:** the infra `k3s` role. Its install task has `creates: /usr/local/bin/k3s`, so it never upgrades an installed node, and it has no ordering or health gating.

**Controller:**
- Vendor `crd.yaml` and `system-upgrade-controller.yaml` from the v0.20.2 release assets.
- The manifest creates ServiceAccount `system-upgrade`, bound to upstream's narrower ClusterRoles (`system-upgrade-controller`: nodes get/list/watch/update, plans, leases; `-drainer`: nodes patch, pods, evictions). That covers cordon, uncordon and job management; the `k3s-upgrade` container itself makes no API calls.
- Set `SYSTEM_UPGRADE_JOB_KUBECTL_IMAGE` per hop (§3). The default `rancher/kubectl:v1.30.3` is used by the **cordon** init container, not only drain, and is out of skew.
- Shipped defaults: job deadline 900 s, backoff limit 99.

**`server-plan`:**
```yaml
spec:
  concurrency: 1
  cordon: true                      # never drain
  serviceAccountName: system-upgrade
  version: v1.32.13+k3s1            # bumped per hop
  nodeSelector:
    matchExpressions:
      - {key: node-role.kubernetes.io/control-plane, operator: In, values: ["true"]}
  upgrade:
    image: rancher/k3s-upgrade
```

**`agent-plan`** (created in Hop 4):
```yaml
spec:
  concurrency: 1
  cordon: true
  serviceAccountName: system-upgrade
  version: v1.35.9+k3s1
  nodeSelector:
    matchExpressions:
      - {key: node-role.kubernetes.io/control-plane, operator: DoesNotExist}
  tolerations:
    - {key: olympus.io/role, operator: Equal, value: management-hub, effect: NoSchedule}
  prepare:
    image: rancher/k3s-upgrade
    args: [prepare, server-plan]
  upgrade:
    image: rancher/k3s-upgrade
```

**Holding naraka-01:**
- Label it `plan.upgrade.cattle.io/agent-plan=disabled` (SUC's own hold) from Phase 0; remove the label in Hop 4.
- SUC's only default toleration is `unschedulable`, so the management-hub toleration above is required.

**Node order within a plan is pseudo-random.** The first server upgraded may be onode-030c31: the etcd leader, the holder of the `k3s`, `k3s-etcd` and `plndr-cp-lock` leases, and the node running local-path-provisioner and metrics-server. Expect an etcd leader election and a VIP move.

## 6. Safety

### Health gate (script; run before each hop and after each server)

**etcd** is checked through k3s's HTTP gateway on `https://127.0.0.1:2382`, run **on each server**. There is no `etcdctl`, and :2379 is gRPC-only. Pass `--cacert/--cert/--key` from `/var/lib/rancher/k3s/server/tls/etcd/server-{ca,client}.*`.
- `member/list` shows the **same 3 member IDs** as the baseline, none `isLearner`, and all nodes `EtcdIsVoter=True`.
- `maintenance/status` reports the same leader on all three, a raftIndex spread under 100, and dbSize recorded.
- `maintenance/alarm` has no alarms.
- `/version` shows the expected `etcdserver`. After Hop 2, `etcdcluster` must read `3.6.0` on all three.

**Kubernetes:**
- 4/4 nodes `Ready`.
- `/readyz` returns ok on each server.
- All Flux Kustomizations and HelmReleases are `Ready`.
- QNAP CSI controller and node pods are `Ready`.
- 11 VolumeAttachments are `attached=true`.
- `k3s certificate check`: certificates expire in 2027, and nothing rotates during the window.

**VIP:**
- `plndr-cp-lock` has a holder.
- From naraka-01, `curl -k https://192.168.253.2:6443/readyz` connects and returns **HTTP 401**. Anonymous auth is off, so 401 means success.

**Crash-looping pods** are compared against a saved **allow-list**, not a zero count. Known noise today: argo-events-controller-manager with 6,663 restarts, and failing `codebase-brain` workflow pods.

### Stop rule

- **Stop conditions:** any gate fails, or a server isn't `Ready` within 10 minutes of its job starting.
- **The rollout halts on its own.** It is one server at a time, so quorum stays at 2 of 3.
- **Before touching anything by hand,** confirm quorum via the 2382 gateway on the two healthy servers.
- **Fix forward on the same version** where possible.
- **A failed job leaves its node cordoned.** After fixing, `kubectl uncordon <node>`.
- **Do not `kubectl delete job`.** SUC recreates it at once and retries.
- **Do not edit the plan to push through.**

### Rollback (restore the pre-hop snapshot)

**Point of no return.** etcd's `etcdcluster` version flips to the new minor (3.6.0 in Hop 2) only when the last server's member joins on the new version. Until then, one failed *secondary* can be reverted without a restore:
- stop k3s;
- `cp -p /usr/local/bin/k3s-<old version> /usr/local/bin/k3s`;
- `rm -rf /var/lib/rancher/k3s/server/db`;
- start k3s. It rejoins via the VIP as a new member, and that member's ID changes.

onode-030c31 can't use this path (it is `cluster-init`, with no `server:` line), so it is never the last server of a hop. After the flip, only the full restore below works. Scheduled snapshots taken after the flip are written by the new etcd and can't be restored by the old binary; only the named `pre-<version>` snapshot on styx can.

**Full restore:**
1. **Stop the upgrade durably, before anything restarts.** Revert the gitops Plan PR (Plan version and kubectl image) and have the revert merged on `main`. A restore rewinds etcd to before the Plan change, so a `flux suspend` or `kubectl delete plan` done now would be undone by the restore. Flux would then re-apply the Plan from `main`, and SUC would re-upgrade the restored servers immediately.
2. **On all three servers:** `systemctl stop k3s`, then `cp -p /usr/local/bin/k3s-<old version> /usr/local/bin/k3s`. Check `k3s --version` shows the old version. Use the copy of the version *immediately before* the hop (e.g. `k3s-v1.32.13+k3s1` for Hop 2), saved and sha256-checked before the hop.
3. **On onode-030c31:** `k3s server --cluster-reset --cluster-reset-restore-path=/var/lib/rancher/k3s/server/db/snapshots/pre-<version>-onode-030c31-<ts>`. Copy the snapshot back from `styx:/mnt/styx-data/k3s-snapshots/` if needed. Then `systemctl start k3s`; wait for Ready and for kube-vip to hold the VIP.
4. **On onode-0312ce, then onode-0314ac:** `rm -rf /var/lib/rancher/k3s/server/db/`, then `systemctl start k3s`. They rejoin via `server: https://192.168.253.2:6443`, so the VIP must answer; otherwise point `server:` at `https://192.168.253.7:6443` temporarily. Verify 3 members via 2382. **Member IDs will be new:** update `EXPECTED_ETCD_MEMBERS` before trusting the gate.
5. **containerd metadata (unverified).** An older containerd may refuse metadata migrated by a newer one. If a node's pods won't start after the binary revert, `rm -rf /var/lib/rancher/k3s/agent/containerd` on that node; its pods restart from their images.
6. **naraka-01:** no action needed. Expect to lose every API write since the snapshot; ESO re-syncs secrets and Flux re-reconciles.

**Snapshots** before each hop:
- `k3s etcd-snapshot save --name pre-<version>`;
- copy it off-cluster to `styx:/mnt/styx-data/k3s-snapshots/`;
- keep `/usr/local/bin/k3s-<old>` on every server.

## 7. Preventing drift afterwards

- **Pin at first install.** Set `k3s_version: v1.35.9+k3s1` everywhere a k3s install can run.
  - The pull inventory already pins `group_vars/compute_hub.yml` and `group_vars/management-hub.yml`.
  - **Find the play/group that installed naraka-01 unpinned and pin it there.** It isn't under `olympus-sdk/infra/push-playbooks/` as originally assumed.
- **No downgrade guard needed.** The role's `creates:` guard already stops reinstalls.
- **Upgrades only through SUC.** Keep SUC installed; patch releases become a `version:` bump. Document that upgrades never go through the role.

## 8. Timing

- **Per server:** about 10 minutes.
- **Soak:** 30 minutes after Hop 1; **24 hours** after Hops 2 and 3.
- **Hop 2 needs a go/no-go,** after etcd 3.5.26 has been healthy for at least 30 minutes on all three servers.
- **Expected impact:** brief control-plane API interruptions and leader elections. Workload downtime is not expected; this is checked during Hop 1, per §2.5.
